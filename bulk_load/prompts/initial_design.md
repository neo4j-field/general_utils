# Initial design decisions

This document records the key design decisions made when scaffolding the
bulk_load module, the alternatives considered, and the empirical evidence
from the first smoke test that shaped the defaults.

## Customer pain point

A Neo4j customer is loading their graph from parquet and consistently
hitting the database's per-transaction memory limit on the relationship
phase. Their shape: 22 node types / 136M rows, 33 rel types / 213M rows,
all rels narrow (2-4 keys + insert_dtm). Customer Aura: 128 GB / 24 CPU.

## Decision 1: Spark Connector over PyIngest

**Considered:** PyIngest (pure Python, simpler ops) vs Spark Connector
(distributed, partition-level parallelism).

**Decision:** Spark Connector. At 349M total rows, partition-level
parallelism matters more than ops simplicity. PyIngest is documented as
an alternative for smaller datasets but not implemented.

## Decision 2: Local Spark mode, not EMR or a cluster

**Considered:** EMR cluster vs local Spark on a single fat VM.

**Decision:** Local mode. Aura is the receiver and has 6 CPUs / one WAL
on the test instance. A bigger Spark cluster cannot push more throughput
through the receiver. Local mode on a same-region VM gives full
performance with zero cluster ops. Same advice applies to the customer
on their 24-CPU Aura: a single fat box running local Spark is enough.

## Decision 3: Same-region GCP VM, not laptop

**Considered:** Run loader from laptop vs VM in same region as Aura.

**Decision:** VM. Empirical: ping to Aura from the VM is 0.286 ms avg.
From a laptop on the public internet it would be 30-80 ms. At 5K-row
batches and ~17,400 batches for 87M rows, latency dominates wall time.
The VM eliminated 9-23 minutes of pure network wait.

VM spec: n2-standard-8 (8 vCPU, 32 GB), Debian 12, 200 GB pd-balanced,
us-east1-b. Matches the receiver-saturating producer profile.

## Decision 4: 1/4 ratio sizing for the test workload

Customer: 128 GB / 136 M nodes / 213 M rels. Test Aura: 32 GB.
We scale node and rel volumes by 1/4 to match the memory ratio:
34 M nodes / 53 M rels. Same 22 node types, 33 rel types. Same
rel-to-node ratio (1.566).

## Decision 5: Synthetic data generated by Python, not by the LLM

**Considered:** Have the LLM generate sample data inline.

**Decision:** Vectorized numpy + pyarrow streaming generator. 87M rows
must not be tokens. Generator streams parquet in 1M-row row groups so
memory stays bounded. Single seed propagates through every per-table
generator for reproducibility.

## Decision 6: Default rel-partitions=1 (set by the smoke test)

**Initial assumption:** rel_partitions=4 with `repartition(N, src_col)`
would be safe — same-source writes group together, no contention.

**What actually happened in the smoke test:**

```
ForsetiClient[transactionId=453] can't acquire EXCLUSIVE
NODE_RELATIONSHIP_GROUP_DELETE(34329) because it would form
this deadlock wait cycle: ... -> tx:453 -> tx:452 -> ... -> tx:453
```

Source-key repartitioning isolates which Spark partition owns writes
for a given source node, but it does NOT prevent two partitions from
writing rels that share a target node. Every relationship write
acquires `EXCLUSIVE NODE_RELATIONSHIP_GROUP_DELETE` on both source AND
target. With random FK distribution, target overlap across partitions
is statistically guaranteed.

**New default: rel_partitions=1.** Documented in README and CLI help
that this is the safe baseline. Raise only after empirical testing on
your specific FK distribution.

Hot rel detection (`--hot-rel-threshold=1000`): rel types whose target
node count is below this force-fall back to 1-partition writes. This
catches dimension tables (RiskRating=5, Channel=20, Currency=50) where
even 2-partition writes deadlock instantly.

## Decision 7: Spark master = `local[*,10]`, not `local[*]`

**Initial assumption:** `spark.task.maxFailures=10` would cause Spark
to retry deadlocked tasks.

**What actually happened:** Plain `local[*]` master silently ignores
`spark.task.maxFailures`. Any task failure (including retriable
`TransientException`) immediately aborted the job ("Task 0 in stage
160.0 failed 1 times").

**Fix:** Use `local[*,N]` master URL syntax (where N is per-task retry
count). Documented but rarely used. We use `local[*,10]`.

## Decision 8: Default `batch.size=5000`, not larger

Customer is hitting transaction memory limit. Common reflex is to
**raise** batch size for better throughput, but that's wrong for narrow
rels on a memory-constrained instance. 5000 is the connector default
and a reasonable starting point. Larger batches = larger transactions
= more memory per commit. Customer's transaction memory issue is
solved by a *modest* value here, not a large one.

## Smoke test outcome

1% scale (~931K rows) end-to-end:
- Generate: ~5s
- Schema setup: ~3s
- Load nodes: ~17s
- Load rels: ~54s
- Total: 76s wall, 13,090 rows/sec effective

Zero deadlocks, zero errors. All 22 node types loaded, all 33 rel
types loaded.

Projected full-scale (87M rows): ~110 minutes at smoke-test rate.
Likely faster in practice because per-table fixed overhead amortizes
better at higher row counts.
